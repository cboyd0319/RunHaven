# Repository Architecture

## Scale assumption

Design repository boundaries for 2,000,000 lines and 50,000 files. Add a unit
only when it has a cohesive capability, manifest, public entrypoint, test seam,
and explicit dependency direction. Do not add empty layers or speculative
services.

## Repository layout

```text
crates/runhaven/          Rust CLI entrypoints
crates/runhaven-cli/      CLI presentation library
crates/runhaven-core/     Shared product and runtime contracts
crates/runhaven-tui/      Codex-derived terminal product surface
src-tauri/                Tauri desktop application
ui/                       React and TypeScript desktop frontend
images/                   Independent Apple container build contexts
scripts/                  Repository-owned verification and operations tools
docs/                     Product architecture and durable operations
third_party/              Isolated third-party source
crates/codex/             Isolated pinned vendored source
```

`crates/` is the shared-library and CLI/TUI Rust source root.
`src-tauri/` is the separate deployable desktop application crate. Each active
child under `crates/` and the Tauri crate is a separate unit in
`repository-structure-policy.json`; an undeclared child crate is rejected. That
policy is also the executable inventory of other approved source roots, units,
manifests, public entrypoints, unit test seams, local documentation, dependency
edges, generated content, vendored content, lockfiles, and temporary exceptions.
Root source files are forbidden unless the policy names the exact file.

The active units are:

| Unit | Manifest | Public entrypoint | May depend on |
| --- | --- | --- | --- |
| `runhaven-core` | `crates/runhaven-core/Cargo.toml` | `crates/runhaven-core/src/lib.rs` | no RunHaven unit |
| `runhaven-cli` | `crates/runhaven-cli/Cargo.toml` | `crates/runhaven-cli/src/lib.rs` | `runhaven-core` |
| `runhaven` | `crates/runhaven/Cargo.toml` | `crates/runhaven/src/main.rs` | `runhaven-cli`, `runhaven-core` |
| `runhaven-tui` | `crates/runhaven-tui/Cargo.toml` | `crates/runhaven-tui/src/lib.rs` | `runhaven-core`, exact pinned crates from the isolated `crates/codex/` workspace |
| `runhaven-tauri` | `src-tauri/Cargo.toml` | `src-tauri/src/lib.rs`, `src-tauri/src/main.rs` | `runhaven-core` |
| `runhaven-ui` | `ui/package.json` | `ui/src/main.tsx` | no repository package |

The base and four agent image contexts under `images/` are independently built
units. `images/common/` is their reusable build-input unit. Each npm-backed
context owns its `package.json`, lockfile, `Containerfile`, and executable
entrypoint where one is required. Image npm scopes are not runtime dependencies
of the UI workspace.

Generated Tauri schemas and permissions live under `src-tauri/gen/` and
`src-tauri/permissions/autogenerated/`. Vendored source stays under
`third_party/` and `crates/codex/`. The comprehensive TUI remains a RunHaven
product surface under `crates/runhaven-tui/`; its pinned upstream-derived source
boundary is not a retirement or permission to delete it.

## Dependency rules

1. `runhaven-core` owns shared runtime truth and depends on no RunHaven unit.
2. `runhaven-cli` may depend on `runhaven-core`.
3. `runhaven` may depend on `runhaven-cli` and `runhaven-core`.
4. `runhaven-tui` may depend on `runhaven-core` and only the exact vendored
   Codex crates declared by the machine policy.
5. `runhaven-tauri` may depend on `runhaven-core`, never `runhaven-cli`.
6. `runhaven-ui` uses the Tauri command contract and may not deep-import Rust or
   another application unit.
7. No other active workspace unit may cross the isolated vendored Codex
   boundary.
8. Unit dependencies use public entrypoints, and the unit graph stays acyclic.

The root Cargo workspace and TypeScript project references encode the native
graphs. `scripts/python.sh scripts/check_repo_layout.py` checks their agreement with the
machine policy and this document.

## Source limits and modularization

Every hand-authored Rust, Python, JavaScript, TypeScript, PHP, Terraform, and
configuration file is reviewed at 300 physical lines or 32,768 bytes and fails
at more than 500 physical lines or 65,536 bytes. Blank and comment-only lines
count. A review warning requires a named modularization decision, not an
automatic split. A split must create cohesive responsibility, a public
contract, and a test seam.

Only exact paths in `non_hand_authored_exclusions` may exempt generated,
vendored, or lock content. A hand-authored temporary exception must name the
exact path, affected rule, owner, reason, temporary ceiling, approval date, and
retirement condition. Globs and directory-wide hand-authored waivers are
invalid.

When an excluded vendored tree contains RunHaven-owned source,
`hand_authored_inclusions` re-enters the exact local files or subtree into the
same review and hard-limit enforcement. A broad vendor label never exempts local
product code.

Enforcement command: `scripts/python.sh scripts/check_file_limits.py`

## Verification

- Fast structure gate: `scripts/check-repo-structure.sh`
- Structure fixtures: `scripts/python.sh scripts/test_file_limits.py` and
  `scripts/python.sh scripts/test_repo_layout.py`
- Session readiness and representative smoke: `./init.sh`
- Full macOS product lane: `scripts/verify-all.sh`

This private pre-alpha repository has no hosted CI. Local checks exercise the
same semantic core against valid and known-violation fixtures. This owner
constraint leaves the canonical hosted-CI enforcement requirement unmet; it is
recorded as a validation gap, not treated as a harness exception.

## Change rules

- Update this file, the machine policy, and executable enforcement together.
- Keep one lockfile owner per ecosystem scope.
- Keep caches, dependencies, build output, generated output, and vendored
  content outside hand-authored source roots.
- Add a unit only when its stable identity and dependency seam are clear.
- Remove a temporary exception when its retirement condition is met.

Product runtime architecture remains in `docs/ARCHITECTURE.md`. That document
does not own repository topology or source-limit policy.
